## 二、核心设计：一个估值函数，两边共用

方案 A 的立身之本是「用行为可信的 AI 猎金人替代真人 PvP」。要做到这点，AI 不能是一套单独的伪装逻辑，它必须和玩家跑同一套规则。

具体落实为 `LootValuation` 这一个静态类：

- 玩家 HUD 判断「这东西值不值得捡」调用它
- AI 猎金人判断「要不要为这个箱子改道」调用它
- 两者判断「该走了」调用同一个 `ShouldHeadForExtraction`
- 两者的背包是同一个 `Inventory` 类，同样的重量上限、同样的超重降速曲线

有一条测试专门守着这个契约：

```
RivalsUseTheSameBagRulesAsThePlayer
  ...第二件重物必须被共用的重量上限拒绝
```

估值函数的形状本身就是玩法：

```
需要达到的价值密度 = 基准 × 时间紧迫度 × 撤离点距离 × 危险度
```

局末、离撤离点远、正被追杀时，门槛会涨到基准的六七倍。这意味着同一件东西在开局值得绕路,在第十五分钟就不值得——这正是搜打撤的核心决策，而 AI 会和玩家在同一时刻做出同样的判断。

AI 的感知也刻意受限于玩家能拥有的信息：视线要过视锥和遮挡检测，听觉只在铃响后的 25 秒内有效，对方身上有多少货只能靠「看见的金光」估。它不读玩家的背包对象。

## 三、近战手感

市场调研 3.1 记录了竞品最响的差评：「明明看着已经砍下去，但判定和反馈总是慢一秒」。那款产品完全取消了锁定。我们的应对不是加回全锁定（那会毁掉近战的走位博弈），而是三件具体的事：

**软锁定，上限 25 度。** 出招瞬间把角色朝向拧向最接近准心的目标，超过 25 度就不管。玩家仍然要瞄，只是不再为差三度而被惩罚。选目标时取「角度偏差最小」而不是「距离最近」——贴脸但在侧后方的敌人不会把你的挥砍抢走。硬核模式把预算设为 0 即可完全关闭，所以这是一个带参数的纯函数而不是全局开关。

**输入缓存。** 收招尾段 0.22 秒内的按键接续连段；更早的按键不丢弃而是缓存，在本次挥砍结束时自动触发。吞输入是「手感差」的另一半原因。

**三层命中反馈 + 命中停顿。** 伤害落地的同一帧同时触发音效、相机冲击、受击者闪白，再叠 60–90 毫秒的全局时停（终结技 1.5 倍）。时停用全局而非单体，因为在单人游戏里整个画面顿一下才读作「打中了」，只停一个角色会读作卡顿。

出招后摇是真实成本：起手阶段移动降到 25%、判定阶段 15%、收招 60%。挥空要付代价，这是近战博弈成立的前提。

## 四、三个 Unity 特有的坑

这一轮的调试时间几乎全花在这三件事上，都不是逻辑错误，而是引擎约定。

### 4.1 一个文件里塞了三个 MonoBehaviour

`RunWorld.cs` 里放了 `Lootable`、`BellTower`、`RunController`。Unity 按文件名匹配 MonoBehaviour 主类，一个 `.cs` 文件对应一个 GUID，所以三个组件在场景里都指向同一个脚本引用，反序列化时互相串。

症状是 PlayMode 测试报「RunController 不在场景里」，但同一次 forge 生成的相机、战利品、主宰、战斗组件全都在。定位方式是把场景文件里 `m_Script` 的 GUID 统计出来，和磁盘上各 `.cs.meta` 的 GUID 对照，发现一个 GUID 出现了三次。

修法就是拆成一类一文件、文件名与类名一致。

### 4.2 编辑期创建的对象不参与序列化

`RivalHunterAgent.Bind()` 原本在 forge 时被调用，在里面直接 `new` 出 brain 和保存引用。这些都是普通字段，不是 `[SerializeField]`，所以保存场景时全部丢失，play mode 下每个 AI 醒来都没有脑子。

修法是把引用改成序列化字段，`Bind()` 只负责写这些字段，brain 本身在 `Awake()` 里构造，另外在 `Start()` 里加了自动查找兜底。雾中主宰有同样的问题，同样处理。

顺带一提，原来的实现还在 `Bind()` 里调用 `gameObject.SetActive(false)` 让主宰保持休眠——这会连 `Start()` 一起阻止，导致它永远不会订阅唤醒事件。现在改成关闭渲染器和灯光，对象本身保持激活。

### 4.3 场景里没有任何碰撞体

程序化生成的 mesh 只有 `MeshFilter` 和 `MeshRenderer`。玩家一进游戏就穿过地面往下掉。

给地面、柱廊、中景墙、前景框加了 `MeshCollider`；碎石和屋顶断梁刻意不加，避免移动被散落细节挂住。

### 4.4 batchmode 下的 deltaTime

PlayMode 测试里用 `Time.deltaTime` 驱动移动，跑 30 帧后玩家只前进了 4 毫米。batchmode 没有渲染负载，一帧只有几十微秒。测试改为传入固定步长 0.05 秒。

这不是引擎缺陷，但值得记：**batchmode 下任何依赖真实帧间隔的测试都是不可靠的**。

## 五、系统清单

### 数据层（纯 C#，无 Unity 依赖，全部有测试覆盖）

| 类型 | 职责 |
| --- | --- |
| `ItemDefinition` / `ItemAffix` / `ItemInstance` | 目录条目、词缀、带词缀的实例。词缀乘数复合，稀有度随词缀数上升并封顶 |
| `Inventory` | 重量与格子双限制；软上限 60% 之上线性降速到 0.55 倍 |
| `LootValuation` | 玩家与 AI 共用的唯一决策函数 |
| `LootTable` / `ItemCatalog` | 种子化掉落，luck 提高词缀数量，同一件不出重复词缀 |
| `RunDirector` | 局内状态机：进入 → 搜刮 → 撤离窗口 → 结算 |
| `RivalHunterBrain` | AI 决策：逃跑 / 撤离 / 伏击 / 战斗 / 抢箱 / 搜刮，每个决策附理由 |
| `SoftLock` | 出招瞄准修正与扇形命中判定 |
| `MeleeStateMachine` | 起手 / 判定 / 收招 / 连段 / 打断 / 输入缓存 |

### 运行时层

| 组件 | 职责 |
| --- | --- |
| `HunterController` | 相机相对移动、冲刺耗体力、负重降速 |
| `OverShoulderCamera` | 越肩机位、弹簧臂、FOV 变化、命中冲击 |
| `MeleeCombatant` | 软锁定、扫描命中、三层反馈、命中停顿 |
| `Damageable` | 生命、体力、受击闪白 |
| `RivalHunterAgent` | 感知采集、把 brain 的决策变成移动 |
| `MistSovereign` | 追猎、施加威胁值、接触即杀 |
| `Lootable` / `BellTower` | 首次交互时才滚内容的容器；摇铃开门 |
| `RunController` / `RunBootstrap` | 局内驱动、输入、交互 |

## 六、测试有效性

63 个 EditMode 测试全绿只能证明它们跑过了。为了证明它们真的守住了逻辑，`tools/mutation_check.sh` 会依次破坏五处关键实现，每次都必须让特定的测试变红：

| 破坏的规则 | 预期变红 | 实际结果 |
| --- | --- | --- |
| 背包不再检查重量上限 | `TryAdd_RejectsItemHeavierThanRemainingCapacity` | 命中，仅此 1 项失败 |
| 超重不再降速 | 两项速度测试 | 命中，恰好 2 项失败 |
| 换装门槛从「好 25%」降到「好一点就换」 | `Appraise_DoesNotSwapOnNearTies` | 命中，仅此 1 项失败 |
| 死亡不再掉落 | `Kill_LosesEverythingCarried` | 命中，仅此 1 项失败 |
| 不摇铃也能进传送门 | `EnterPortal_FailsWhenNoWindowIsOpen` | 命中，仅此 1 项失败 |

每次破坏后都还原，最终基线回到 0 失败。

## 七、当前缺口

| # | 缺口 | 说明 |
| --- | --- | --- |
| 1 | AI 猎金人不会真的战斗 | 决策层会输出 Fight，但执行层只走到目标身边，没有攻击与受击互动 |
| 2 | AI 不会真的捡东西 | `ExecuteLootCall` 已实现且有测试，但执行层还没在到达容器时调用它 |
| 3 | 无 UI | 背包、重量、威胁、撤离倒计时全部只存在于数据里，屏幕上看不到 |
| 4 | 无音频 | 三层命中反馈中的音效层挂了接口但没有音源资产。恐怖与紧张氛围里音频权重极高 |
| 5 | 无动画 | 角色是静态网格，移动与挥砍都没有骨骼动画。这是目前与商业水准差距最大的一项 |
| 6 | 局外营地不存在 | 撤离后的战利品入库、设施升级、职业解锁都还没有 |
| 7 | 只有一张手工布局的地图 | 概念文档承诺的模块化程序化拼装尚未实现 |
| 8 | 无存档 | |

第 5 项需要角色建模与骨骼动画，程序化手段无法解决，是接下来最大的实际工作量。
