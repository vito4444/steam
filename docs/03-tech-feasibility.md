### 安装方式说明

没有走 Unity Hub，而是直接下载官方编辑器 tarball 解压。原因是 Unity Hub 的 AppImage 在无 FUSE 的容器里不可靠，而 tarball 方式没有额外依赖。Windows 构建模块官方只提供 `.pkg`（macOS 安装包）格式，用 `7z` 解开 xar 容器取出 `Payload~`（cpio 归档），再解到编辑器的 `PlaybackEngines` 目录下即可，Unity 编辑器不检查模块的来源格式。

### 版本选择理由

选 `6000.0.81f1` 而不是最新的 `6000.3.22f1`：`6000.0.x` 是 Unity 6 的第一个长期支持线，补丁号已经到 81，稳定性经过充分验证。`6000.3.22f1` 在调研当天（2026-08-13）才发布，不适合作为一个要发行到 Steam 的项目的基础版本。

## 三、软件渲染截图能力（已验证）

这是「边运行边自检、截图看差距」这个需求的技术地基，必须实测。

### 验证方法

用 Unity 无头模式（`-batchmode`）配合 Xvfb 虚拟显示器，通过一个编辑器脚本程序化生成场景（1 个平面、25 个不同高度的立方体、1 盏方向光、1 台 FOV 35° 的透视摄像机），然后把摄像机渲染到 `RenderTexture`，读回像素并编码成 PNG 写盘。

关键命令形态：

```bash
export LIBGL_ALWAYS_SOFTWARE=1
export GALLIUM_DRIVER=llvmpipe
xvfb-run -a -s "-screen 0 1920x1080x24" \
  /opt/unity/6000.0.81f1/Editor/Unity \
  -batchmode -quit \
  -projectPath <项目路径> \
  -executeMethod <编辑器方法> \
  -logFile <日志路径>
```

注意：**不能加 `-nographics`**。加了这个参数 Unity 会完全不初始化图形设备，`Camera.Render()` 会得到全黑。截图任务必须让 Unity 走真实的 OpenGL 路径，靠 Xvfb + llvmpipe 提供软件实现。构建任务则可以加 `-nographics` 以加快速度。

### 实测结果

| 指标 | 数值 |
| --- | --- |
| 端到端耗时（启动编辑器 → 建场景 → 渲染 → 写盘 → 退出） | **6.4 秒** |
| 输出分辨率 | 1280×720，2× 抗锯齿 |
| 输出文件 | 93,861 字节 PNG |
| 画面正确性 | 透视、方向光漫反射、明暗过渡、深度排序全部正确 |

### 这个结果意味着什么

1. **自动化视觉自检是可行的，而且很快。** 6.4 秒一轮意味着可以在每次代码提交后自动跑几十个视角的截图，成本可以忽略。
2. **构图完全可复现。** 摄像机位置、角度、FOV 全部由脚本指定，同一份场景数据每次渲染出的画面在像素级别是一致的（除非渲染代码本身改了）。这让「视觉回归检测」成为可能——画面变了就是有东西改了。
3. **软件渲染的画面和真机画面不完全一致。** llvmpipe 实现的是 OpenGL 标准，但抗锯齿、各向异性过滤、某些后处理效果的具体表现会和真实 GPU 有差异。**因此软件渲染截图适合验证「构图、比例、布局、明暗关系、颜色」，不适合验证「画质、特效精细度、帧率」。** 后者必须在有 GPU 的机器上验证。

### 对方案选择的直接影响

| 方案 | 软渲染截图的可信度 | 原因 |
| --- | --- | --- |
| B: OVERCLOCK | **极高** | Unlit + Emission 渲染路径在软件和硬件上的结果几乎相同 |
| A: ABYSSAL | 高 | 全烘焙光照，无实时阴影，差异主要在 Bloom 的具体表现 |
| D: SALVAGE | 中 | 有一盏实时阴影灯，软件渲染的阴影质量会明显不同 |
| C: NIGHT SHIFT | 中低 | 手电筒实时阴影 + 程序化关卡，画面不可复现 |
| E: DEAD DROP | **低** | 体积雾 + 蒙皮动画 + 动态战斗，软件渲染下既慢又不准 |

## 四、Windows 构建能力

### 可以做到的（已验证）

**StandaloneWindows64 + Mono 脚本后端的交叉编译已经实测通过。** Linux 版编辑器安装 `WindowsStandaloneSupport` 模块后，能构建出完整的 Windows 64 位可执行文件，可以直接上传到 Steam 并被玩家运行。

实测数据：

| 项 | 结果 |
| --- | --- |
| 构建结果 | `Succeeded`，0 错误 |
| 产物总大小 | 86,480,555 字节（约 82 MB，空场景基线） |
| 产物结构 | `TechProbe.exe`（671 KB）、`UnityPlayer.dll`（34 MB）、`UnityCrashHandler64.exe`、`TechProbe_Data/`、`MonoBleedingEdge/`、`D3D12/` |
| 构建耗时 | 约 3 分钟（4 核 CPU，冷缓存，含首次导入资源） |

产物结构完整，包含 D3D12 支持目录和 Mono 运行时，这是 Unity Windows 发行版的标准布局。

### 不能做到的

- **IL2CPP 脚本后端的 Windows 构建：已确认不可用。** IL2CPP 会把 C# 转译成 C++，然后需要用 MSVC 编译链接成原生代码。MSVC 只在 Windows 上存在，Linux 编辑器无法调用。

  **这个限制对 Steam 发行的实际影响：** Mono 后端完全可以正式发行，Steam 上大量商业游戏用的就是 Mono。区别是：IL2CPP 的运行时性能通常好 10–30%，且代码更难被反编译。对于本项目的候选方案（都不是性能极限型游戏），Mono 完全够用。如果后期确实需要 IL2CPP，必须在一台 Windows 机器上做最终构建。

- **在本机运行 Windows 构建产物**：没有装 wine。可以装，但 wine 下跑 Unity 游戏的可靠性一般，用它做自动化验证会引入大量假阳性。**更好的做法是：自动化验证全部用 Linux 构建产物做，Windows 构建只在发布前做产物完整性检查（文件结构、依赖 DLL、版本号），实际运行验证在你的 Windows 机器上做。**

### 双构建策略

```
同一份 Unity 项目
  ├── Linux 64 构建 → 在本机 Xvfb 里跑，做自动化玩法测试和运行时截图
  └── Windows 64 构建 → 交付产物，上传 Steam
```

两个构建来自完全相同的场景和脚本，行为差异只可能来自平台相关代码（文件路径、输入设备）。只要不写平台特定代码，Linux 上验证通过的逻辑在 Windows 上就是对的。

## 五、自动化自检流水线设计

这一节回应「边运行边自检优化，同时截图看自己和目标的差距」这个需求。整套流水线分四层，从快到慢、从便宜到贵。

### 第 0 层：纯逻辑测试（无 Unity，秒级）

游戏的核心系统（方案 B 的热扩散和流量图、方案 A 的钻进模型和故障传播）应该写成**不依赖 UnityEngine 命名空间的纯 C# 类库**。这样它们可以：

- 用 `dotnet test` 直接跑单元测试，不启动 Unity
- 被批量模拟脚本调用，一秒钟跑几千次仿真
- 用于自动化平衡性调优：跑一万局，统计胜率分布、资源曲线、构筑强度，找出数值失衡点

**这是整套流水线里价值密度最高的一层。** 它能在不渲染任何画面的情况下回答「这个游戏好不好玩」的一大半问题（数值是否平衡、系统是否有深度、是否存在必胜策略）。

### 第 1 层：Unity 编辑器批处理测试（十秒级）

用 Unity Test Framework 的 EditMode 和 PlayMode 测试，在 `-batchmode` 下运行：

```bash
Unity -batchmode -runTests -testPlatform EditMode -testResults results.xml -projectPath <项目>
```

覆盖：资源引用完整性、场景加载、预制体配置正确性、序列化数据合法性。

### 第 2 层：定点截图与视觉对比（分钟级）

这是「截图看差距」的核心实现。

#### 2.1 定点截图

在项目里定义一组**视觉基准点**（Visual Benchmark Points），每个基准点是一条记录：

```
基准点ID | 场景 | 摄像机位置 | 摄像机旋转 | FOV | 时间/状态设定 | 对应的目标参考图
```

每次自检时，编辑器脚本遍历所有基准点，逐个渲染并保存 PNG。因为参数全部固定，同一个基准点在不同版本之间的画面是可以直接逐像素对比的。

建议的基准点数量：核心场景 8–12 个，覆盖玩家最常看到的构图。

#### 2.2 与「目标」的差距量化

「目标」有两类，要分开处理：

**类型一：与上一个版本对比（视觉回归）**

计算当前截图和上一版截图的：
- 逐像素差异图（直接输出一张高亮显示变化区域的图）
- 结构相似度（SSIM）
- 变化像素占比

用途：检测「我改了 A，结果 B 也变了」这类意外回归。这个是完全客观的，可以设阈值自动报警。

**类型二：与概念图/参考游戏截图对比（美术方向差距）**

这类对比不可能做到逐像素，但可以量化以下几个维度：

| 指标 | 计算方法 | 说明的问题 |
| --- | --- | --- |
| 主色板 | 对图像做 k-means 聚类（k=6），取聚类中心和占比 | 「我的画面和概念图的配色差多远」 |
| 亮度直方图 | 转灰度后统计分布，取均值、中位数、暗部占比、亮部占比 | 「我的画面是不是太亮/太平」 |
| 对比度 | 灰度标准差 | 「明暗层次够不够」 |
| 饱和度分布 | HSV 空间 S 通道的均值和分布 | 「颜色是不是太灰/太艳」 |
| 边缘密度 | Canny 边缘检测后的边缘像素占比 | 「画面细节量差多少」 |
| 构图重心 | 亮度加权的质心坐标 | 「视觉焦点位置对不对」 |

这六个指标能覆盖美术方向差距的绝大部分，而且全部可以用 Python + Pillow/NumPy 计算，不需要额外依赖。

**但指标不能代替判断。** 最终还需要把「当前截图」和「目标参考图」并排拼成一张对比图，由我（或你）实际去看，然后写出具体的差距清单，例如：「暗部太灰，概念图的暗部是接近纯黑的，需要把环境光从 0.08 降到 0.02」。**指标负责发现问题，肉眼负责定位原因。** 这两步都要有。

#### 2.3 输出物

每轮自检产出一个目录：

```
selfcheck/<时间戳>/
  ├── shots/               # 本轮所有基准点截图
  ├── diff-vs-prev/        # 与上一版的差异图
  ├── compare-vs-target/   # 与概念图的并排对比图
  ├── metrics.json         # 六项量化指标的数值
  └── report.md            # 自动生成的指标摘要 + 人工写的差距清单
```

### 第 3 层：运行时行为验证（分钟级）

构建 Linux 版本，在 Xvfb 里实际运行，游戏内脚本按预设脚本操作（用录制的输入序列或直接调用游戏逻辑接口），并在关键节点截图和记录状态。

```bash
xvfb-run -a -s "-screen 0 1920x1080x24" \
  ./Build/linux64/Game.x86_64 -batchmode -autotest -scenario <场景名> -logfile <日志>
```

覆盖：完整游玩流程能否跑通、有没有卡死、存档读档是否正确、内存是否泄漏。

**注意：这一层测不了帧率。** llvmpipe 的性能和真实 GPU 差两三个数量级，本机跑出来的帧率数字没有参考价值。性能测试必须在有 GPU 的机器上做。

### 自检的触发时机

| 时机 | 跑哪几层 |
| --- | --- |
| 每次代码改动后 | 第 0 层 |
| 每次提交前 | 第 0 + 1 层 |
| 每个功能完成后 | 第 0 + 1 + 2 层，并生成对比图给你看 |
| 每个里程碑 | 全部四层 + Windows 构建产物检查 |

## 六、进度可视化：给你看的东西

你提到「定时发送概念图和目前成果图，一是让我心里有数，二是让你知道差距如何去修改优化」。落实成具体机制：

### 每个里程碑必须产出的四样东西

1. **目标概念图** —— 这个里程碑想达到的画面（AI 生成或参考图）
2. **当前成果图** —— 定点截图里最有代表性的 2–3 张
3. **并排对比图** —— 上面两者拼在一起，加上量化指标标注
4. **差距清单** —— 逐条列出「概念图有而成果图没有的东西」，每条附上打算怎么改

### 差距清单的写法

不写「画面还需要打磨」这种话。要写成可执行的条目：

```
差距 1：暗部层次
  概念图：暗部接近纯黑（亮度中位数 0.06），只有告警灯是亮的
  成果图：暗部发灰（亮度中位数 0.23），整体扁平
  原因：环境光强度设成了 0.15，且没有开 Bloom 的阈值过滤
  改法：环境光降到 0.02，Bloom 阈值提到 1.2

差距 2：控制台密度
  概念图：视野内约 40 个可辨识的仪表/旋钮
  成果图：视野内 11 个
  原因：只做了主控制台，侧面板还是空的
  改法：补 3 组侧面板，每组 8–10 个元件（复用现有模型）
```

## 八、技术栈决定

基于以上所有验证结果，推荐的技术栈：

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 引擎版本 | Unity 6000.0.81f1 LTS | 已安装验证；LTS 线补丁充分 |
| 渲染管线 | **URP**（Universal Render Pipeline） | 性能好、跨平台一致、软件渲染下可用。HDRP 在无 GPU 环境完全不可行 |
| 图形 API（编辑器/Linux） | OpenGLCore | Vulkan 无软件驱动 |
| 图形 API（Windows 发行版） | Direct3D11 优先，OpenGLCore 作为后备 | 玩家机器上 D3D11 兼容性最好 |
| 脚本后端 | Mono | IL2CPP 在 Linux 上无法交叉编译到 Windows |
| .NET 版本 | .NET Standard 2.1 | 兼容性最好 |
| 核心逻辑组织 | 独立于 UnityEngine 的纯 C# 程序集 | 让第 0 层测试成为可能 |
| 输入系统 | Unity Input System（新版） | 支持手柄，Steam Deck 兼容需要 |
| 版本控制 | Git + Git LFS（二进制资产） | 仓库已有 git-lfs |
| 目标平台 | StandaloneWindows64（主）+ StandaloneLinux64（自动化测试用） | |

## 九、复现步骤

如果需要在另一台机器上重建这套环境，完整步骤在 `tools/setup-unity.sh`。核心是四步：

1. 装系统依赖（Mesa、Xvfb、7z、cpio 等）
2. 下载并解压 Unity Linux 编辑器 tarball
3. 下载 Windows 支持模块 `.pkg`，解出 `Payload~`，展开到 `PlaybackEngines/WindowsStandaloneSupport`
4. 用 `Unity.Licensing.Client --activate-ulf` 激活许可证

许可证凭据不入库，通过环境变量 `UNITY_EMAIL` 和 `UNITY_PASSWORD` 传入。
